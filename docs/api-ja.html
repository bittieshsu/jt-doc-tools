API 利用ガイド

Jason Tools ドキュメントツールボックスは外部に RESTful API を提供しており、すべてのツールに対応するエンドポイントがあります。自動化のフロー、自社システム、スケジュール処理に組み込めます。

基本方針：API は既定では認証なしで使えます（web UI と同じ公開範囲です）。制限が必要なときは、管理者が admin の「API Token」ページで enforce モードを有効にし、bearer token を発行します。

1. 認証

認証を有効にしない（既定）

新規インストールでは既定で認証が無効なため、すべての /api/* をそのまま利用でき、token は不要です。

1. 認証

API token を有効にする

管理者は admin → API Token へ移動します：

  1. 「新しい token を発行」をクリック → 用途の名称を入力（例 gitlab-ci）→ 64 文字の hex token を受け取ります（一度しか表示されないので保存してください）
  2. 「Enforce —— token を持たないものはすべて拒否」にチェックを入れて保存します

以降、すべての /api/* には次のいずれかの形式が必要です：

Authorization: Bearer 64char-hex-token-here

または query string：

GET /api/jobs/abc123?token=64char-hex-token-here

token がない、または無効な場合 → 401 Unauthorized の JSON：

{"ok": false, "detail": "需要有效的 API token（Authorization: Bearer ...）"}

Token は admin / jtdt CLI で管理し、web 認証 (jtdt-admin / LDAP / AD) とは完全に独立しています。

3. 文書変換 API

オフィス文書 → PDF

オフィス文書を PDF に変換します（OxOffice / LibreOffice エンジンを使います）。

POST /api/convert-to-pdf
パラメータ種類必須説明
filefile✓オフィス文書 の文書
curl -X POST http://localhost:8765/api/convert-to-pdf \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@報告.docx" \
  --output 報告.pdf

レスポンス：PDF のバイナリ（application/pdf）。失敗時は 4xx + JSON {"detail": "..."}。

3. 文書変換 API

オフィス文書の形式変換

同じ種類の文書どうしの形式変換：文書ファイル↔文書ファイル、表計算↔表計算、プレゼンテーション↔プレゼンテーション。job モードで job_id を返します。

先に利用できる変換先の形式を問い合わせてから変換を送信してください。 target の値はインストール環境によって異なるため（Impress モジュールがなければプレゼンテーションの組は現れません）、id を自分のプログラムに固定で書かないでください：

GET /tools/office-convert/formats
curl -s http://localhost:8765/tools/office-convert/formats \
  -H "Authorization: Bearer YOUR_TOKEN" | jq
# → {"families": [{"id": "text", "name": "文書檔",
#                  "sources": ["odt", "docx", ...],
#                  "targets": [{"id": "docx-2007", "ext": "docx",
#                               "label": "Word 2007", "note": "...",
#                               "common": true}, ...]}, ...]}
POST /tools/office-convert/convert
パラメータ種類必須説明
filefile✓オフィス文書。複数回指定できます（複数の場合は ZIP にまとめます）
targetstr✓変換先の形式 id。上の formats から取得します

同じリクエストの中のファイルは同じ種類でなければなりません（表計算と文書ファイルを混ぜて送ることはできません）。また target の属する種類とも一致している必要があり、そうでない場合は 400 を返します。

# 文書檔：.odt 轉成 Word 97–2003
curl -X POST http://localhost:8765/tools/office-convert/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@報告.odt" -F "target=doc" | jq
# → {"job_id": "...", "download_url": "/api/jobs/.../download"}

# 簡報：.pptx 轉成 ODF 簡報
curl -X POST http://localhost:8765/tools/office-convert/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@簡報.pptx" -F "target=odp" | jq

.docx / .xlsx / .pptx にはそれぞれ 2 つの変換先があり、違いは次のとおりです互換モード名称だけの違いではありません：

変換先の id出力互換モード
docx-2007Word 2007 の書き方12
docx-365Word 2010–365 の書き方15
xlsx-2007 / xlsx-ooxmlExcel 2007–365 / Office Open XML—
pptx-2007 / pptx-ooxmlPowerPoint 2007–365 / Office Open XML—

レスポンス：{"job_id": "...", "download_url": "..."}。1 ファイルなら元の形式、複数なら ZIP を返します。 失敗時は 4xx + JSON {"detail": "..."}。

3. 文書変換 API

PDF → Office

PDF を Word（.docx）または OpenDocument（.odt）に逆変換します。job モードで job_id を返します。

POST /tools/pdf-to-office/convert
パラメータ種類必須説明
filefile✓PDF
output_formatstrdocx（既定）/ odt
enginestr変換エンジン：pdf2docx-refine（既定、安定）/ jtdt-reform（自社のレイアウト再構成）/ jtdt-layout（レイアウト再現：LibreOffice/OxOffice Draw で正確にインポートし、自社の変換エンジンで docx/odt に再構成します。レイアウトがほぼ 1:1 のページ固定テキストボックスで、画像 / 枠線を含みます。本質はフロー型のテキストではなく、本物の表もありません）
enable_postprocessboolpdf2docx-refine のみ有効：jtdt-refine の後処理（25 の fixer）を適用するか。既定は false
# 預設引擎 pdf2docx-refine
curl -X POST http://localhost:8765/tools/pdf-to-office/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@form.pdf" -F "output_format=docx" \
  | jq
# → {"job_id": "...", "download_url": "/api/jobs/.../download"}

# 改用自家 jtdt-reform 引擎
curl -X POST http://localhost:8765/tools/pdf-to-office/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@form.pdf" -F "output_format=odt" -F "engine=jtdt-reform" \
  | jq

# 改用 jtdt-layout 版面重現引擎（表單 / 多欄 / 含框線表格版面最接近原 PDF）
curl -X POST http://localhost:8765/tools/pdf-to-office/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@form.pdf" -F "output_format=odt" -F "engine=jtdt-layout" \
  | jq

レスポンス：{"job_id": "...", "download_url": "..."}。その後は第 10 章の job API でポーリングして結果を取得します。

変換の前後を比較するサムネイルの取得：job の完了後、GET /api/jobs/{job_id} の meta.preview に page_indices（プレビュー対象の 0 始まりのページ番号の一覧。6 ページ以下なら全部、7 ページ以上なら先頭 2 + 中央 2 + 末尾 2）、 orig_pages、result_pages、orig_chars、result_chars が含まれます。ページごとのサムネイルは次で取得します：

GET /tools/pdf-to-office/preview/{job_id}/orig/{page}     # 轉換前（原 PDF）
GET /tools/pdf-to-office/preview/{job_id}/result/{page}   # 轉換後（docx/odt 渲染）

page は 1 始まりのページ番号です（次に対応します page_indices の要素 +1）。次を返します image/png。

# 完成後讀 preview 頁碼清單
curl -s http://localhost:8765/api/jobs/$JOB \
  -H "Authorization: Bearer YOUR_TOKEN" | jq '.meta.preview'
# 取第 1 頁的前 / 後對照縮圖
curl -s http://localhost:8765/tools/pdf-to-office/preview/$JOB/orig/1 \
  -H "Authorization: Bearer YOUR_TOKEN" --output before_p1.png
curl -s http://localhost:8765/tools/pdf-to-office/preview/$JOB/result/1 \
  -H "Authorization: Bearer YOUR_TOKEN" --output after_p1.png

4. PDF 編集 API

PDF → プレゼンテーション

PDF を PowerPoint（.pptx）または OpenDocument プレゼンテーション（.odp）に逆変換します。1 ページが 1 枚のスライドに対応し、 スライドサイズは原本のままです（縦向きの PDF もそのまま再現します）。job モードで job_id を返します。

エンジンは 1 つだけ（jtdt-layout のレイアウト再現）のため、engine パラメータはありません。

POST /tools/pdf-to-slides/convert
パラメータ種類必須説明
filefile✓PDF
output_formatstrpptx（既定）/ odp
curl -X POST http://localhost:8765/tools/pdf-to-slides/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@deck.pdf" -F "output_format=pptx" \
  | jq
# → {"job_id": "...", "download_url": "/api/jobs/.../download"}

# 輸出 OpenDocument 簡報（物件多時比 .pptx 快）
curl -X POST http://localhost:8765/tools/pdf-to-slides/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@deck.pdf" -F "output_format=odp" \
  | jq

前後比較のサムネイルは pdf-to-office と同じです：

GET /tools/pdf-to-slides/preview/{job_id}/orig/{page}     # 轉換前（原 PDF）
GET /tools/pdf-to-slides/preview/{job_id}/result/{page}   # 轉換後（簡報渲染）

job の完了後、GET /api/jobs/{job_id} の meta.stats に pages（スライド枚数）、 images、objects（オブジェクトの総数）が含まれます。

環境の要件：office スイートの次が必要です Impress モジュール（oxoffice-impress / libreoffice-impress）。モジュールがないと「変換は成功したのに出力が見つからない」という状態になります。 「設定 → 依存パッケージの確認」で確認できます。

POST /tools/meeting-transcribe/api/meeting-transcribe
パラメータ種類必須説明
filefile✓音声 .m4a / .mp3 / .wav / .aac / .ogg / .opus / .flac、動画 .mp4 / .mov / .mkv / .webm

num_speakersstring既定は 0 で、サービス側の判断に任せます。0 のままを推奨します

num_speakers が尋ねているのは「発言量が識別に足りる人数」であり、出席人数ではありません。音声サービスが中国語の会議 20 件（AISHELL-4 test、5〜7 人）で測定したところ、正しい人数を指定した場合と指定しなかった場合に有意な差はありませんでした（13.24% 対 12.46%、対応のあるブートストラップの 95% 信頼区間 [−2.72, +4.10] は 0 をまたぎます）。「より正確になる」ことを期待して入力しないでください。

本当の理由は仕組みにあります。同じ 20 件では、最適なクラスタ数が実際の人数を上回ったことは一度もありませんでした（10 件で一致、10 件で少ない、上回ったのは 0 件）。6 人がその場にいても、音響的に 6 グループに分けられるとは限りません。無理に 6 つに分けると、システムは最も多く話した人を分割するしかなくなり、それが最も高くつく誤りです。ひとことふたことしか話していない人は数えず、迷う場合は 0 のままにしてください。

このエンドポイントは同期処理です。37 分の会議で実測 7〜8 分（認識 ＋ 発言者分離 ＋ 校正）かかるため、呼び出し側のタイムアウトは長めにしてください。バックグラウンド処理が必要な場合は Web 側の経路（POST /upload → POST /start → ジョブ ID で /api/jobs/{id} をポーリング）を使ってください。

  -F "file=@meeting.m4a" \

  -F "num_speakers=0" | jq

  "source": {"filename": "meeting.m4a", "size_bytes": 17823213},
  "remote_job_id": "job_01M34PVW581P2QD3Q0YFT5Y903",
  "status": "succeeded",
  "uncorrected": false,
  "layers": {"raw": 1045, "final": 1045, "speakers": 1045},
  "summary": {"correction_level": "punctuation_only", "correction": {"edited": 612}},
  "segments": [
    {"seq": 1, "text": "各位早，我們開始。", "speaker": "S1",
     "start_ms": 1450, "end_ms": 2650}
  ]

segments は 3 つのレイヤーを統合したものです。テキストは校正後のレイヤー、タイムスタンプは元の認識レイヤー、発言者は speakers レイヤーから取り、seq で対応づけます。対応しないセグメントは無理に結びつけません。そのセグメントに発言者が付かないほうが、他人の名前を貼り付けるよりましだからです。

context は文字起こしを読み解くためだけに使われ、項目の出所にはなりません。「誰々は運用担当副社長で議長」と分かれば誰が指示し誰が担当かの判断に役立ちますが、背景に書かれた事柄は会議では起きていません —— 決議・タスク・リスク・未決事項は必ず文字起こしから抽出されます。プロンプトで明示するほか、二つの仕組みで担保しています。引用検証（項目は文字起こしの段落を指していなければならず、背景は比較対象に含まれません）と、「背景と非常に似ており、かつ文字起こしより明らかに似ている」ものを破棄する処理です。破棄されたものは dropped_count に計上されます。

この端点は同期処理です。2 時間の会議では数分かかります（モデルへのリクエストは約 30〜60 回）ので、呼び出し側のタイムアウトを長めにしてください。バックグラウンド処理が必要な場合は web 側の経路（POST /upload → POST /start → ジョブ ID を /api/jobs/{id} でポーリング）を使ってください。

先に管理画面で LLM を有効にしてください。無効な場合は 503 を返します。文字起こしが読み取れない場合は 400 を返します（対応形式をメッセージで示します）。

オフィス文書全体を別の言語に翻訳し、同じ形式・同じレイアウトのファイルを返します —— テキストだけを置き換え、 レイアウトは組み直しません。.doc / .docx / .odt、.xls / .xlsx / .ods、 .ppt / .pptx / .odp に対応します。

PDF は受け付けません：PDF には段落がなく、テキストは位置の決まった断片です。長さの違う訳文に置き換えると レイアウトは必ず崩れます。PDF を翻訳するには下の「一文ずつ翻訳」をお使いください。

POST /tools/doc-translate/api/doc-translate

Form（multipart）：

項目種類必須説明
filefile✓オフィス文書（上記 9 種類の拡張子）
target_langstr翻訳先の言語。既定は zh-TW
source_langstrauto（既定）/ en / ja / ko …
domainstr分野のヒント（法律契約、診療レポート…）。専門用語の精度を高めます
curl -X POST http://localhost:8765/tools/doc-translate/api/doc-translate \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@contract.docx" \
  -F "target_lang=en" \
  -F "domain=法律合約" \
  -o contract_translated.docx

レスポンスは翻訳後のファイルそのものです（Content-Disposition: attachment）。形式はアップロードしたものと同じです。

このエンドポイントは同期です：全体を翻訳し終えてから応答するため、大きなファイルではリバースプロキシのタイムアウトに達します。 web インターフェースはバックグラウンドジョブ版を使います（POST /tools/doc-translate/start、 送信後は次で進捗を確認し /api/jobs/{job_id} 、完了後は次で GET /tools/doc-translate/download/{upload_id} ファイルを取得します）。 admin による LLM サービスの有効化が必要です（/admin/llm-settings）。無効の場合は次を返します 503。

Shell：job の完了を監視してダウンロード

#!/bin/bash
TOKEN="YOUR_TOKEN"
API="http://localhost:8765"

JOB=$(curl -fsSL -X POST "$API/api/llm-review" \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@filled.pdf" -F "template_id=vendor_form_v3" \
  | jq -r .job_id)

echo "Job: $JOB"

while :; do
  S=$(curl -fsSL "$API/api/jobs/$JOB" -H "Authorization: Bearer $TOKEN")
  STATE=$(echo "$S" | jq -r .status)
  PROG=$(echo "$S" | jq -r .progress)
  echo "  $STATE  $PROG"
  [ "$STATE" = "completed" ] && break
  [ "$STATE" = "failed" ] && { echo "Failed"; exit 1; }
  sleep 2
done

curl -fsSL "$API/api/jobs/$JOB/download" \
  -H "Authorization: Bearer $TOKEN" \
  --output reviewed.pdf
echo "Saved: reviewed.pdf"

14. レート制限 / 大きなファイルの上限

現時点で rate limit は内蔵していません。導入時にはリバースプロキシ（nginx / Caddy）で次を追加することをおすすめします：

  • client_max_body_size 100M（必須。設定しないと大きな PDF が拒否されます）
  • proxy_read_timeout 900s + proxy_send_timeout 900s（必須 —— LLM ツールの推論は 1 件あたり 5-15 分かかることがよくあり、既定の 60s では必ず 504 になります）
  • proxy_buffering off（LLM の streaming に適しています）
  • 多層の nginx 構成（自前の LLM proxy + jt-doc-tools で nginx が 2 台）ではどの層にも設定が必要です。1 層でも既定のままだと、その時点で切れます
  • 外部に公開する必要がある場合は、悪用を防ぐために limit_req_zone の追加をおすすめします

詳しくは OPS.md の「リバースプロキシ」の節と「504 Gateway Timeout のトラブルシューティング手順」をご覧ください。

14b. ユーザーのワークスペース（session 認証。Bearer API ではありません）

「マイワークスペース」はログイン session に紐づく web 機能で（cookie 認証）、外部向けの Bearer API ではありません。各ファイルがログインしたアカウント単位で分離されるためです。admin が「ワークスペース設定」で有効にする必要があり、無効のときは以下のエンドポイントはすべて 404 を返します。

エンドポイントメソッド説明
/workspaceGET「マイワークスペース」ページ
/workspace/api/listGET自分のファイルを一覧表示（?accept=pdf,png で絞り込み）+ 容量 + 保持時間
/workspace/api/countGETファイル数（サイドバーのバッジ用）
/workspace/savePOST保存：job_id（サーバー側で job の結果を複製）または file（bytes を直接アップロード）。PDF / PNG のみ
/workspace/file/{file_id}GETファイルの取得（?dl=1 でダウンロード）
/workspace/thumb/{file_id}GETサムネイル（PDF は 1 ページ目をレンダリング / PNG は元画像）
/workspace/deletePOST削除（file_id）
/workspace/renamePOST名前の変更（file_id、name）

容量の割り当て、1 ファイルの上限、保持時間、有効 / 無効は admin が /admin/workspace で設定します（全体で統一され、個別の例外はありません）。

14c. ユーザーの通知と受信トレイ（session 認証。Bearer API ではありません）

§14b のワークスペースと同じ性質で、ログイン session（cookie）に紐づくため、外部向けの Bearer API ではありません。 内容がログインしたアカウント単位で分離されるためです。未ログインの場合は常に 401 / 302 を返します。

エンドポイントメソッド説明
/api/my/notifyGET自分の通知設定を読み取ります（ジョブの完了時に通知するか、どのチャネルを使うか）
/api/my/notifyPOST自分の通知設定を保存します
/api/my/inboxGETサイト内通知の一覧（未読を優先）
/api/my/inbox/seenPOST既読にする（id または all=1）

この 4 つは意図的に Bearer API に含めていません：返すのは「このログインしたユーザーの」データであり、 token で呼び出しても意味がないためです（token はユーザーに紐づきますが、これらのエンドポイントはブラウザーからの利用を想定しています）。
